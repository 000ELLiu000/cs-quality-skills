# 动态 Rubric 生成指南

## 核心理念

不同任务类型有不同的质量风险点，不能一套固定标准打天下。动态 Rubric 是根据任务上下文自动生成的专属质检维度，聚焦该任务最核心、最可能出问题的点。

## 生成规则

### 输入依赖

Rubric 生成**只依赖**以下信息（不看样本内容）：

- `task_type`：任务类型
- `task_goal`：任务目标
- `skill_info`：执行 Skill 的说明文档或 Prompt 摘要

样本内容在「按 Rubric 执行检查」环节使用，不参与 Rubric 生成。

### 数量约束

- 生成 **3-5 个**维度
- 不少于 3 个（否则覆盖不足）
- 不多于 5 个（否则太散失去重点）

### 质量约束

每个维度必须满足：

1. **不与前两层重复**：不能是 3C 已覆盖的内容，不能是通用四维度已覆盖的内容。注意：此约束仅要求 Rubric 维度的「内容」不与前两层重复，不意味着可以跳过 Rubric 生成。无论前两层覆盖了多少内容，都必须生成 3-5 个专属维度并执行检查
2. **可操作性**：检查要点和通过标准必须具体到可以判断「通过 / 不通过」
3. **贴合任务**：必须与该任务的 task_type、task_goal 直接相关
4. **有区分度**：该维度能区分出好产物和差产物

### 权重分配

每个维度赋予权重：

- **高（high）**：该维度不通过会直接影响产物可用性，触发高风险
- **中（medium）**：该维度不通过会影响产物质量但不至于不可用
- **低（low）**：该维度不通过是优化项

权重分配原则：
- 至少 1 个高权重维度
- 高权重不超过 2 个
- 与 task_goal 中明确要求的点对应的维度，权重应为高

## 不同任务类型的关注方向

### 数据生产

| 关注方向 | 说明 | 典型维度示例 |
|----------|------|-------------|
| 话术与信号联动 | 生成内容是否与输入信号 / 模板正确对应 | 「客服回复是否引用了对应场景的话术模板」 |
| 场景多样性 | 批量生成时是否存在高度雷同 | 「多条样本之间的表述多样性」 |
| 角色一致性 | 对话中角色是否保持人设不串戏 | 「客服是否全程保持专业人设」 |
| 对话合理性 | 轮次、结局、转折是否自然 | 「对话结局与过程是否逻辑一致」 |
| 标签准确性 | 元数据标签是否与内容一致 | 「difficulty 标签是否与实际对话复杂度匹配」 |
| few-shot 遵循度 | 生成内容是否遵循了 few-shot 示例的风格和结构 | 「格式和风格是否与 few-shot 示例一致」 |

### 数据评测

| 关注方向 | 说明 | 典型维度示例 |
|----------|------|-------------|
| 归因准确性 | 评分理由是否真正支撑评分结论 | 「扣分理由是否能在原文中找到依据」 |
| 标签一致性 | 同类问题是否给出一致的评判 | 「相似样本的评分是否一致」 |
| 评分粒度合理性 | 评分是否区分度足够 | 「是否所有样本都给了同一个分数」 |
| 边界 case 判断 | 模糊情况是否处理得当 | 「模棱两可的 case 是否有合理的判断依据」 |
| 维度覆盖 | 是否按要求覆盖所有评估维度 | 「评测是否遗漏了某个评估维度」 |
| 统计指标正确性 | 汇总统计是否与逐条结果一致 | 「准确率等统计指标是否计算正确」 |

### 数据修复

| 关注方向 | 说明 | 典型维度示例 |
|----------|------|-------------|
| 修复完整性 | 所有需修复的点是否都被修复 | 「原始数据中的所有错误是否都被纠正」 |
| 数据同步正确性 | 修复是否正确同步到相关联字段 | 「修改了 A 字段时，依赖 A 的 B 字段是否同步更新」 |
| 修复副作用 | 修复是否引入新问题 | 「修复操作是否破坏了原本正确的内容」 |
| 版本一致性 | 修复后数据格式是否与最新标准一致 | 「修复后的数据是否符合当前版本的 schema」 |
| 修复溯源 | 是否保留修复记录 | 「是否能看出哪里被修改了、为什么修改」 |

### 数据质检

| 关注方向 | 说明 | 典型维度示例 |
|----------|------|-------------|
| 质检标准一致性 | 质检结论是否与质检标准一致 | 「扣分项是否与质检维度对应」 |
| 证据充分性 | 每个判定是否有原文支撑 | 「问题标注是否有原文摘录作为证据」 |
| 质检覆盖率 | 是否检查了所有应检维度 | 「是否遗漏了某个应检的质检维度」 |

## 输出格式

### 生成的维度定义

```json
{
  "dimension_name": "维度名称（简短、明确）",
  "check_points": "具体检查什么（1-2 句话）",
  "pass_criteria": "什么情况算通过（可操作的判断标准）",
  "weight": "高 | 中 | 低"
}
```

### 执行结果

```json
{
  "dimension_name": "维度名称",
  "weight": "高 | 中 | 低",
  "status": "通过 | 不通过",
  "issues": [
    {
      "sample_id": "样本ID",
      "description": "具体问题",
      "evidence": "问题内容摘录"
    }
  ]
}
```

## 防止退化的自检

生成 Rubric 后，自我检查以下三个问题：

- 这些维度是不是换个任务也能用？→ 如果是，说明不够贴合，需重新生成
- 去掉某个维度会不会遗漏关键风险？→ 如果不会，说明该维度不必要
- 这个维度能否基于样本内容给出明确的通过 / 不通过判断？→ 如果不能，说明不够可操作

## 生成 Prompt

```
你是一个自动化任务的质检专家。请根据以下任务上下文，生成该任务的专属质检维度（Rubric）。

【任务上下文】
任务类型：{task_type}
任务目标：{task_goal}
使用Skill：{skill_name}
Skill说明：{skill_description}
参考知识库：{reference_knowledge}

【要求】
1. 生成的质检维度应针对该任务类型的核心质量风险点
2. 每个维度需包含：维度名称、检查说明（check_points）、预期通过标准（pass_criteria）
3. 优先从以下角度思考：
   - 该任务类型最容易出错的环节是什么？
   - 该 Skill 的产出物最常被人工质检打回的原因是什么？
   - 任务目标中是否有容易被忽略的细节要求？
4. 生成的维度数量建议 3-5 个，聚焦最关键的质量点
5. 根据 references/dynamic-rubric-guide.md 中不同任务类型的关注方向，确定该任务类型的重点检查维度
6. 为每个维度标注权重（高/中/低），至少 1 个高权重维度

请输出 JSON 格式的 Rubric 定义：
{
  "rubric_dimensions": [
    {
      "dimension_name": "维度名称",
      "check_points": "具体检查什么",
      "pass_criteria": "什么情况算通过",
      "weight": "高 | 中 | 低"
    }
  ]
}
```
