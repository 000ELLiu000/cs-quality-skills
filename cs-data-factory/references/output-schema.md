# 输出数据 Schema

> 用途：定义最终产出的训练数据格式，与算法侧要求对齐。
> 全链路节点输入/输出 Trace 见 `references/checkpoint.md`。

---

## 字段说明

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `会话id` | string | ✅ | 格式：`gen_{路径编号}_{Persona编号}_{会话序号}_t{轮次}`，如 `gen_P002_P1_001_t1` |
| `消息时间` | string | ✅ | 格式：`YYYY-MM-DD HH:MM:SS`，同一会话各轮同一时间即可 |
| `历史消息` | string | ✅ | 截至当前轮的完整对话，格式见下 |
| `话术回复` | string | ✅ | 这一轮客服应该说的话（模型预测目标） |
| `话术关联动作` | string | ✅ | 客服说完这句话时直接触发的后台操作，无需用户确认；无操作填 `"无"` |
| `话术共识动作` | string | ✅ | 需要用户明确认可才能执行的操作；无操作填 `"无"` |
| `所有信号` | string | ✅ | 多行文本，格式与真实样本完全一致（含 `### 用户信息`、`### 支付信息` 等 section headers）；详见下方格式说明 |
| `外呼信号` | string | ✅ | 外呼发生前为「无外呼记录」，发生后填外呼结果 |

### 所有信号字段格式（v2.0 模板替换架构）

v2.0 架构下，「所有信号」的输出格式与真实样本完全一致，包含原始的 section headers 和所有信号 key（含补集信号）。格式由真实样本的第一行自动提取为模板，不硬编码任何 section 名称。

```
### 用户信息
{用户标签:高价值用户}
{用户等级:金卡会员}

### 订单信息
{订单退款状态:无退款}
{订单使用信息-订单状态:全部已使用}
{订单对应的品牌名称:某知名连锁火锅品牌}

### 支付信息
{支付金额:152.00}
{支付方式:微信支付}

### 商户信息
{开票联系商户电话:1XXXXXXXXXX}
{门店电话:空}
```

信号值的三种来源及优先级：

- **路径信号（judgment）**：来自骨架 SOP 的判断信号，值由路径锁定。骨架 `order_signals` 为最高优先级权威来源。
- **参考信号（slot）**：LLM 按 `signal_rules.json` 中的 `mock_rule` 生成的话术槽变量（含从 other+dynamic 提升的信号）。
- **补集信号（other+static）**：从真实样本池中 round-robin 取用的静态信号值，保持与真实数据分布一致。

### 信号组装流程

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1. 提取模板 | `parse_signal_template()` | Phase 0 从真实样本第一行提取，值替换为 `__PLACEHOLDER__`，存入 `signal_rules.json` |
| 2. 合并生成信号 | `_merge_generated_signals()` | 合并骨架判断信号 + LLM mocked 信号为扁平 dict（骨架优先） |
| 3. 分配补集信号 | round-robin 从 `other_signal_pool` | 每个 session 分配一组补集信号值（来自真实样本按 session 聚合的池） |
| 4. 模板填充 | `fill_signal_template()` | 将生成信号 + 补集信号值填入模板占位符，输出最终文本 |

### v1.0 降级模式

当 `signal_rules.json` 不存在或不含 `signal_template` 时，自动降级为简化格式（仅含 `### 路径信号` + `### 参考信号`，不含补集信号），向后兼容旧 SOP。

---

### 动作字段说明

**话术关联动作**：客服发出话术时同步触发的工具操作，不需要用户二次确认。
- 示例：`"外呼商家-开发票"`（客服说"我帮您联系商家"时直接发起外呼）
- 无操作时：`"无"`

**话术共识动作**：需要先得到用户明确同意，才能执行的操作。
- 示例：`"取消订单"`（需用户说"好的，可以取消"后才执行）
- 无操作时：`"无"`
- 每条数据最多一个共识动作

**动作枚举**：具体可用的动作标签由 SOP 文件中各节点的动作定义决定，以最新 SOP 为准。

## 历史消息格式

```
用户：用户第一句话\n
客服：客服第一轮回复\n
用户：用户第二句话\n
客服：客服第二轮回复\n
用户：用户第三句话\n
```

规则：
- 每条消息以「用户：」或「客服：」（**全角冒号**）开头，末尾加 `\n`
- 历史消息只包含截至**当前轮之前**的内容（不含当前轮客服回复）
- 第一轮：历史消息只有用户的开场白

## 一个会话拆成多条的规则

路径P002（3个节点）× P1，会生成以下几条数据：

| 条目 | 历史消息 | 话术回复 | 外呼信号 |
|---|---|---|---|
| 第1轮 | `用户：开发票！！\n` | 客服建议联系商家 | 无外呼记录 |
| 第2轮 | 第1轮完整历史 | 客服收尾（有其他问题吗）| 无外呼记录 |

路径P003（6个节点，含外呼），外呼后的轮次外呼信号要更新为实际结果。

## 生产质量要求

- 客服话术：口语化，自然，不生硬
- 用户话术：符合 Persona 特征
- 信号：与路径节点严格对应，不捏造矛盾值
- 参考信号：话术中引用的具体数值（品牌名、电话、金额等）必须与 `mocked_signals.参考信号` 中的值一致
- 不同 Persona 下，客服话术主体逻辑不变，可在措辞/共情表达上有差异
