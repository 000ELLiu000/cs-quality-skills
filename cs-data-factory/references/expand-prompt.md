# cs-expand：生产 Prompt 模板

> 用途：Phase 1 生产时，`generate_prompts.py` 自动读取并填充变量，构造每条任务的 LLM 调用 Prompt

---

## Prompt 模板

```
你是一个平台客服对话生成专家。你的任务是模拟真实客服场景，生成符合客服话术规范示例的对话数据。

## 角色与规范（必须贯穿全程）
{SPEECH_GUIDELINES}

## SOP路径骨架
{PATH_CONTENT}

{SIGNAL_MOCK_RULES}
{EMOTION_GUIDELINES}
## 当前用户 Persona
{PERSONA_NAME}：{PERSONA_DESC}
用户特征：{PERSONA_FEATURES}
用户风格示例（真实对话片段，仅供语气/节奏/连发习惯参考，行为方向以路径骨架为准）：
{PERSONA_EXAMPLES}

## 输出要求
本次请一次性生成 **{OUTPUT_COUNT} 条**独立对话样本，每条对话对应同一路径、同一Persona，但措辞、用户表达、细节各不相同。

严格按以下JSON格式输出（一个JSON数组，包含 {OUTPUT_COUNT} 个对话对象），不要输出任何其他内容（不要加```json等标记）：

[
  {
    "会话id": "gen_{PATH_ID}_{PERSONA_ID}_{BATCH}_s1",
    "消息时间": "YYYY-MM-DD HH:MM:SS",
    "mocked_signals": {
      "判断信号": {
        "信号名": "你为本 session 选定的值（必须来自骨架已锁定的枚举值，不可更改）"
      },
      "参考信号": {
        "信号名": "你为本 session mock 的值（按 mock 规则生成，全程保持一致）"
      }
    },
    "turns": [
      {
        "role": "user",
        "content": "用户说的话"
      },
      {
        "role": "agent",
        "content": "客服说的话",
        "话术关联动作": "直接触发的操作，无则填「无」",
        "话术共识动作": "需用户确认的操作，无则填「无」",
        "outbound_update": null
      }
    ]
  },
  {
    "会话id": "gen_{PATH_ID}_{PERSONA_ID}_{BATCH}_s2",
    "消息时间": "YYYY-MM-DD HH:MM:SS",
    "mocked_signals": { ... },
    "turns": [ ... ]
  }
]

说明：
- 输出一个顶层 JSON 数组，包含恰好 {OUTPUT_COUNT} 个对话对象
- 会话id 后缀依次为 _s1, _s2, ..., _s{OUTPUT_COUNT}
- mocked_signals 字段必须包含：判断信号（来自骨架锁定值）+ 参考信号（按 mock 规则生成）
  - 判断信号的值必须与骨架中「当前场景信号（已由SOP路径锁定）」完全一致，不可更改或二次创作
  - 参考信号的值由你在生成对话前 mock，全 session 保持一致，对话中引用的话术数据须与此一致
  - 动态信号（session 内可变）不需要在 mocked_signals 中列出，直接在对话生成时自然演进
- turns 按对话顺序排列，role 只有 "user" 和 "agent" 两种
- role=agent 的轮次必须包含：话术关联动作、话术共识动作、outbound_update
- outbound_update：本轮话术关联动作包含外呼时填写，未触发外呼填 null。**此字段必须是完整的客服-商家通话多轮对话记录，严格禁止填写任何摘要性语句（如「外呼结果：...」「商家表示...」「客服致电...」等），只允许输出纯对话内容（每行以「客服:」或「商家:」开头，2~6轮）；对话结论必须与路径锁定的外呼结果枚举值保持一致**
- role=user 的轮次只包含 role 和 content，不包含其他字段
- 对话以用户首次发起咨询开始，客服先确认用户诉求，再按骨架推进
- **{OUTPUT_COUNT} 条对话必须在以下维度上有明显差异：(1) 总轮次数不同（如 s1 共6轮、s2 共9轮，不得相同）；(2) 用户开场和铺垫方式不同（直接说诉求 / 先发图 / 先抱怨 / 先追问背景，各条选用不同方式）；(3) 措辞、情绪节奏、细节各异；严禁复制粘贴或仅改几个词**

## 约束
1. 严格按检查点顺序推进对话，不跳过检查点，不自行发明处理方式；检查点之间的过渡对话可自由发挥，不受限制；**用户不认可方案时，此处不属于检查点定义的骨架节点，可自由生成 2-4 轮拉扯对话（用户提异议 → 客服承接再劝），之后再推进到下一检查点**
2. 【用户话语生成规则】用户首先表达诉求，客服确认后按检查点推进；用户在每个态度锚点处**应该用多句话表达**（尤其是情绪化/维权型 Persona，参考 Persona 定义中情绪等级≥mid 的类型），每个锚点对应的用户轮次**至少包含2条连续用户消息**，体现追问、反驳、情绪递进；Persona 控制「怎么说」，分支走向由锚点锁定不可更改；**【方案拒绝/拉扯规则】用户不认可客服方案时，不得直接接受或沉默，应从新角度提出异议（如追问原因、表达委屈、质疑平台责任），客服重新承接情绪 + 解释 + 再劝，拉扯轮次视情绪等级可达 2-4 轮，情绪化/维权型 Persona 尤其需要体现**；**【情绪演变规则】用户情绪不是一成不变的：开头情绪激动，被安抚后可能出现新的不满点再激动，最终趋于接受；不要从开头到结尾情绪一直平稳**；**【图片消息规则】在线客服渠道下（非电话场景），用户有时会发图来证明情况或提供信息，图片消息格式为：`【图片】##图片链接=mock->系统识别图片结果:XXX`，其中 XXX 为图片内容描述（如"已使用的订单详情，包含商家名称XXX""显示一组对话，商家回复说无法开发票"等，内容与当前对话语境一致，自由发挥）；不是每次对话都需要发图，根据语境自由决定是否插入，一次对话图片消息不超过2条；情绪化/维权型 Persona 更有可能发图（参考 Persona 定义中倾向发图的类型）**；**【口语化规则】用户消息的书写风格须符合所在 Persona 的真实线上表现：口语化程度高的 Persona（参考 Persona 定义中语言特征标注"口语化"或"极简"的类型）的用户消息应体现打错字、缺标点、极简单词（如"发票""退了""开"）、语义模糊等特征；不要把用户消息写得过于完整规范；各 Persona 的口语化程度参照 Persona 定义中的语言特征**；**【无视规则】低配合度 Persona（参考 Persona 定义中合作度=low 的类型），有时会无视客服上一条消息，直接继续说自己的诉求或重复抱怨（体现"自顾自"行为）；此类行为一次对话插入1-2处为宜**；**【脏话规则】强维权型 Persona（参考 Persona 定义中标注"强维权"的类型）在情绪激烈时应生成脏话（如"傻逼""草泥马""真的脑瘫""放屁"），在最激动的节点自然出现，一次对话1-2处；情绪化抱怨型 Persona（参考 Persona 定义中标注"情绪化抱怨"的类型）偶尔在极度不耐烦时出现（最多1处）；其他 Persona 不生成脏话；脏话出现后客服不正面回应脏话本身，只承接情绪继续推进方案**
3. 【客服话术生成规则】骨架中内嵌的话术示例仅供语气和表达风格参考，**禁止照抄或仅改数字/人称**；同一检查点在不同 session 中的话术必须有明显差异，可变化的维度包括：情绪承接方式（直接安抚/迂回共情/先肯定诉求）、背景交代顺序、劝说角度（从平台立场/从用户利益/从时间成本）、过渡语和收尾方式等；口语化、自然、体现共情，不要模板腔；**客服每轮回复必须响应用户刚才说的具体内容**（如用户发了图要明确回应图片内容，用户说了特定背景要引用该背景，用户提了转人工要承接该诉求），禁止忽略用户实际内容直接套用通用安抚句；多句话之间用换行分隔，**严禁用 `/` 拼接**；高情绪 Persona（情绪化抱怨型/强维权型，参考 Persona 定义中情绪等级≥mid 的类型）时，客服第一句必须先承接情绪（如「理解您的感受」「确实给您添麻烦了」），再给出方案；**有背景信息可交代时（如外呼结果、平台规则原因），先简要说背景再给方案，不可直接抛方案**；**给方案时必须有情感引导或劝说（如"虽然…但…您看可以吗"），不能仅事务性确认**；**结束语须基于本次对话的实际走向自然生发，不得套用固定句式：先回顾这次对话发生了什么（问题解决了还是未解决、用户情绪是平静还是带着遗憾离开、等了多久、中间经历了什么波折），再从这个具体情境里生长出收尾的话，措辞和情感基调要与整段对话的"温度"保持一致；问题已解决时可以带一点正向期待，问题未解决或用户带着遗憾离开时不要强行正面、改为轻声致歉或表示随时可以回来；每条对话的结束语必须措辞各异、严禁复制或仅换一个词**；以下套话**任何时候均严格禁止（含开场白和追问场景）**：
   - 「非常感谢您对我们平台的支持」
   - 「非常感谢您的耐心等待」（用户明显不耐烦/情绪激动时尤其禁止）
   - 「您好！感谢您联系XX客服」
   - 「请问有什么可以帮您的」/ 「有什么可以帮到您」（任何时候均禁止，包括对信息缺失型 Persona 的追问；改用如「看到您联系我们，能告诉我是什么情况吗」「辛苦您说一下具体情况」「请您描述下遇到的问题」）
   **【转人工应对规则】**用户提出"转人工""找真人""要换个人"等诉求时，客服不得表态自己的身份（不说"我是AI"也不说"我是人工"），而应从解决问题角度承接：先表示"我现在就在处理您的问题"或"我可以直接帮您解决这件事"，再明确说明自己当前能做什么，继续推进流程；此类场景可在情绪化/维权型 Persona（参考 Persona 定义中情绪等级≥mid 的类型）的对话中自然插入1次。**【情绪转折过渡规则】**情绪激动的用户在态度锚点转向「认可」时，不应一句"好吧"直接断崖落地；转折前须有2-3句过渡，体现疲惫认命（"行吧行吧，你们就这规定"）、带遗憾接受（"那就算了，以后不来了"）、将信将疑（"那就先试试吧，不行我再来找你"）等方式；态度方向锁定为「认可」，但情绪余温可以保留，甚至可以带一句牢骚再认可；**情绪化/维权型 Persona 的情绪着陆尤其不应干净利落**。
4. 话术关联动作/话术共识动作必须**严格来自对应检查点的定义**，不可推断或自行发明；未定义的动作一律填「无」；两个字段不可省略，即使都是「无」也必须显式写出；**若参考信号中包含具体金额字段（如赔付金额、退款金额），执行对应动作时话术关联动作必须包含真实数值**（如「操作红包赔付-3元」，而非「操作红包赔付」）；金额为区间时，模型自行选定区间内一个值后全程保持一致
5. outbound_update 只有在该轮话术关联动作包含外呼时才填非 null 值，其他情况一律填 null；**此字段必须是多轮纯对话文本（每行「客服:」或「商家:」开头，2~6轮），严格禁止摘要性语句（如「外呼结果：...」「商家表示已...」）；对话结论必须与骨架锁定的外呼结果枚举值严格一致**
```

## 变量说明

| 变量 | 填入内容 | 来源 |
|---|---|---|
| `{PATH_CONTENT}` | 路径骨架（含场景信号、动作序列、内嵌话术参考、用户反应） | `generate_prompts.py` → `build_path_content()` |
| `{SIGNAL_MOCK_RULES}` | 信号 Mock 规则块（骨架之后注入，告知 LLM 如何 mock 参考信号；规则为空时为空字符串） | `data/sop/{sop_id}_signal_rules.json` → `generate_prompts.py` → `build_signal_mock_rules()` |
| `{PERSONA_NAME}` | 如「P1：急迫催促型」 | `references/persona.md` |
| `{PERSONA_DESC}` | Persona 一句话描述（耐心/合作度） | `references/persona.md` |
| `{PERSONA_FEATURES}` | 典型特征 + 示例说法 | `references/persona.md` |
| `{SPEECH_GUIDELINES}` | 客服话术规范全文 | `assets/speech-guidelines.md` |
| `{PATH_ID}` | 如 P002 | 路径文件 |
| `{PERSONA_ID}` | 如 P1 | persona.md |
| `{BATCH}` | 001 起递增的批次号，同路径×Persona 多次生产时递增 | `generate_prompts.py` → `next_seq()` |
| `{OUTPUT_COUNT}` | 单次调用生成的样本数，默认 5，由 `--samples N` 控制 | `generate_prompts.py` → `args.samples` |
| `{EMOTION_GUIDELINES}` | 情绪处理规范全文（可选，文件不存在时为空字符串） | `data/sop/{sop_id}_emotion.md`（按 sop_id 自动加载） |

### {SIGNAL_MOCK_RULES} 内容说明

`{SIGNAL_MOCK_RULES}` 由 `generate_prompts.py` 从 `data/sop/{sop_id}_signal_rules.json` 中构造，格式示例：

```
## 信号 Mock 规则（骨架优先）

> **骨架中已明确给出的判断信号值，不得修改，直接用于 mocked_signals.判断信号。**
> 以下规则仅适用于需要 mock 的参考信号（slot 类型）。

**参考信号 mock 规则**（session 开始前 mock，全程保持一致）：
- 订单对应的品牌名称：从骨架枚举值中选取（骨架已锁定，如"指定品牌"则可选择具体品牌名）
- 开票联系商户电话：随机生成 11 位手机号（1开头，第二位3-9）
- 支付金额：在合理区间内随机生成（如 10-500 元，保留2位小数）
```

- **判断信号（judgment）**：骨架路径已经锁定了枚举值（如「订单状态=全部已使用」），prompt 中只需提示 LLM 确认这些值，不需要 mock
- **参考信号（slot）**：SOP 里需要填入话术的槽位信号（品牌名、电话、金额等），提供 mock 规则让 LLM 自行生成，保证话术与信号一致
- **其他信号（other）**：新架构下不再注入 prompt，也不再出现在 final.jsonl 的「所有信号」字段中
- **规则文件不存在**：`{SIGNAL_MOCK_RULES}` 为空字符串，行为与旧架构（无信号 mock 指令）一致

### mocked_signals 输出格式说明

LLM 在每个 session 对象中输出 `mocked_signals` 字段，`postprocess.py` 从中提取，组装最终「所有信号」：

```json
"mocked_signals": {
  "判断信号": {
    "订单退款状态": "无退款",
    "订单使用信息-订单状态": "全部已使用"
  },
  "参考信号": {
    "订单对应的品牌名称": "某连锁火锅品牌",
    "开票联系商户电话": "1XXXXXXXXXX",
    "支付金额": "88.50"
  }
}
```

- `判断信号` 中的值必须与骨架锁定值完全一致（`postprocess.py` 校验）
- `参考信号` 中的值为 LLM 按规则 mock 的结果，全 session 一致
- 最终「所有信号」字段格式：判断信号 + 参考信号合并（不含补集信号）
